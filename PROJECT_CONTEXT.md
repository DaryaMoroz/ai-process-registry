# Актуальный контекст проекта «ИИ-агент анализа реестра процессов»

**Статус документа:** актуальный источник принятых проектных решений  
**Методика scoring:** `1.1`  
**Статус проекта:** `READY FOR CODEX`

## 1. Назначение документа

Документ фиксирует текущее согласованное состояние проекта. При принятии нового решения этот файл обновляется с заменой устаревшей формулировки; противоречащие варианты не сохраняются параллельно.

Нормативные документы текущего этапа:

1. `SCORING_ENGINE_SPEC.md` — единственный нормативный источник формальных правил scoring.
2. `REGISTRY_MAPPING_MLH.md` — нормативный профиль импорта реестра МЛХ.
3. `scoring_config_v1.1.yaml` — машиночитаемое представление методики scoring `1.1`.
4. `MVP_PASSPORT_AND_BACKLOG.md` — утверждённые scope, этапы и backlog MVP.
5. `TECH_SPEC.md`, `REGISTRY_SCHEMA.md`, `TEST_CASES.md` — синхронизированные требования, концептуальная модель данных и приёмочные сценарии.

При расхождении применяются: `SCORING_ENGINE_SPEC.md` для scoring, `REGISTRY_MAPPING_MLH.md` для Excel/mapping и `MVP_PASSPORT_AND_BACKLOG.md` для scope и этапов. YAML не вводит правила, которых нет в спецификации scoring.

## 2. Цель MVP

Система принимает официальный реестр процессов без его изменения, строит отдельный аналитический слой, помогает собрать и подтвердить недостающие факты и детерминированно рассчитывает оценки:

- `Ценность /25`;
- `Реализуемость /25`.

Основное представление приоритетов — матрица `Ценность × Реализуемость`. Сумма `/50` не является основным способом сравнения процессов.

## 3. Неизменяемый официальный источник

- Официальный реестр используется только для чтения.
- Исходный Excel не изменяется и не перезаписывается.
- Формулы Excel не пересчитываются.
- Parser читает сохранённые в книге cached values.
- Если cached value отсутствует, содержит Excel error или не интерпретируется однозначно, `normalized_value = null` и создаётся `DataQualityIssue`.
- Дополнительные факты, результаты интервью, подтверждения, конфликты, риски, blockers и score snapshots хранятся только в отдельном аналитическом слое.

Файл `МЛХ_последняя_редакция_с_изменениями.xlsx` является только тестовым примером результатов обследования и интервью и не определяет структуру официального реестра.

## 4. Пилотный mapping-профиль МЛХ

| Параметр | Значение |
|---|---|
| `profile_id` | `registry_mlh` |
| `mapping_version` | `1.0.0` |
| Поддерживаемые форматы | `.xlsx`, `.xlsm` |
| Лист по умолчанию | `Лист3` |
| Фактический диапазон пилота | `A8:S17` |
| Строка заголовков | `8` (`A8:S8`) |
| Строки данных | `9–17` |
| Официальных колонок | `19` (`A:S`) |

Архитектура Parser поддерживает явный выбор другого листа. Такой лист принимается только после валидации по `REGISTRY_MAPPING_MLH.md`; отсутствие или неоднозначность требуемой структуры не компенсируется предположениями.

Фактическая классификация строк `Лист3`:

| Тип | Номера строк |
|---|---|
| `PROCESS` | `9, 10, 11, 12, 14, 17` |
| `AGGREGATE` | `13, 15, 16` |

Допустимые типы строк: `PROCESS`, `GROUP_HEADER`, `AGGREGATE`, `TOTAL`, `EMPTY`, `UNKNOWN`. Только `PROCESS` может иметь `scoring_eligible = true`; `UNKNOWN` в scoring не участвует.

## 5. Единица анализа

- Единица первичного анализа — строка официального реестра, классифицированная как `PROCESS` и представляющая самостоятельный исполняемый процесс.
- Для каждой такой строки создаётся ровно одна первичная `AnalysisUnit`.
- Формальный scoring выполняется по `AnalysisUnit`, а не напрямую по Excel-строке.
- После интервью первичная строка может быть декомпозирована на несколько внутренних `AnalysisUnit` без изменения официального реестра.
- Заголовки групп, агрегирующие, итоговые, пустые и неизвестные строки не получают scoring.

## 6. Идентичность и версии

Разделяются три понятия:

- `source_row_id` — идентификатор строки конкретной загрузки;
- `process_id` — внутренний стабильный идентификатор процесса;
- `source_fingerprint` — версионированное средство сопоставления процесса между версиями реестра.

Номер строки Excel и официальный код процесса не являются постоянным `process_id`. Код процесса не считается гарантированно уникальным. Номер строки, лист, версия загрузки, изменяемые метрики и рассчитанные scores не входят в fingerprint. Неоднозначное сопоставление между версиями не разрешается автоматически: создаются новый `process_id`, issue и задача на решение человеком.

Версионируются как минимум:

- исходная загрузка и checksum файла;
- `mapping_version`;
- `fingerprint_version`;
- `methodology_version`;
- конфигурация scoring;
- `input_snapshot_id` для каждого расчёта.

## 7. Факты и evidence

Статус факта хранится отдельно от его источника.

| Статус | Значение |
|---|---|
| `Confirmed` | факт подтверждён допустимым источником или человеком |
| `Derived` | результат детерминированного преобразования подтверждённых входов с полной provenance |
| `Inferred` | гипотеза или извлечение LLM, ещё не подтверждённое человеком |
| `Unknown` | значение неизвестно; в данных хранится `null` |

Допустимые `source_type`: `registry`, `calculated`, `interview`, `document`, `system_data`, `llm_hypothesis`; роль источника хранится отдельно. `Derived` не является источником: для него обязательно сохраняются входные факты, формула/правило и версия преобразования. Human confirmation и иные решения сохраняются как отдельные `Confirmation`/`HumanDecision` и audit evidence.

LLM может извлекать и структурировать сведения, формировать `FactCandidate`, вопросы, гипотезы и признаки противоречий. До подтверждения человеком LLM-extracted fact остаётся `Inferred` и не участвует в formal scoring.

## 8. Стадии scoring

### 8.1. PRE-SCORE

Использует только:

- `Confirmed Registry Facts`;
- `Derived Facts`, детерминированно рассчитанные только из таких фактов.

PRE-SCORE может быть неполным и содержит coverage и диапазон возможного результата.

### 8.2. INTERVIEW-SCORE

Может использовать подтверждённые человеком факты интервью, документов или систем и Derived facts из допустимых подтверждённых входов. Неподтверждённые `FactCandidate` не используются. Результат может оставаться неполным.

### 8.3. VERIFIED SCORE

Допускается только если:

- все 10 критериев имеют значения `1–5`;
- нет `null` среди результатов критериев;
- evidence каждого критерия имеет статус `Confirmed` или допустимый `Derived`;
- отсутствуют неразрешённые конфликты, влияющие на scoring;
- выполнены специальные требования к evidence из `SCORING_ENGINE_SPEC.md`;
- сохранены `methodology_version` и `input_snapshot_id`.

Подтверждённый `BLOCKER` может существовать одновременно с `VERIFIED SCORE` и не обнуляет оценку.

## 9. Rule Engine

- Rule Engine — единственный вычислитель formal scores.
- Методика: `1.1`.
- Нормативные правила: `SCORING_ENGINE_SPEC.md`.
- Машиночитаемая конфигурация: `scoring_config_v1.1.yaml`.
- Все thresholds, enum mappings, обязательные входы, missing behavior и правила агрегации загружаются из валидированной конфигурации.
- Одинаковые `input_snapshot_id` и `methodology_version` дают одинаковый результат.
- Значение `Unknown` никогда не преобразуется в `1` или предполагаемое значение.

Обязательные методические уточнения:

- F1: `confirmed_no_access → 1`, `unknown → null`;
- F2–F5: при нескольких подтверждённых применимых правилах берётся минимальный score; неизвестное ограничение не снижает score автоматически, но создаёт `RISK_REQUIRES_VERIFICATION`; при недостаточности данных score равен `null`;
- V3: подтверждённый `manual_work_share_percent` полностью заменяет PRE proxy в текущем расчёте; proxy сохраняется в истории; несовпадение proxy с фактом само по себе не является conflict;
- конфликт двух или более подтверждённых фактических источников делает затронутый criterion result равным `null` до решения человеком.

Для каждой оси сохраняются `full_score`, `known_sum`, `coverage` и `min/max range`. `full_score` появляется только при наличии всех пяти критериев оси.

## 10. LLM Agent

LLM используется для:

- проведения интервью;
- извлечения и структурирования потенциальных фактов;
- выявления недостающей информации;
- поиска возможных противоречий;
- формирования уточняющих вопросов;
- объяснения формального результата на основе трассировки Rule Engine.

LLM не:

- назначает formal score;
- заменяет `null` предположением;
- подтверждает собственные гипотезы;
- изменяет официальный реестр;
- изменяет утверждённые правила scoring.

## 11. Conflicts, risks и blockers

- `Conflict` фиксирует несовместимые подтверждённые факты. Затронутый score остаётся `null` до явного `HumanDecision`.
- `Risk` фиксирует ограничение или неопределённость, требующую внимания. Для неизвестного потенциального ограничения используется `RISK_REQUIRES_VERIFICATION`.
- `Blocker` хранится отдельно от score и имеет собственное evidence и статус подтверждения.
- Неподтверждённый возможный blocker остаётся гипотезой/риском и не становится подтверждённым blocker автоматически.

## 12. Компоненты MVP

Согласованный поток:

`Registry Parser → Registry Mapping → Data Quality → Process Analysis Card → Rule Engine → Backend/Orchestrator → LLM Agent → UI`

Backend/Orchestrator управляет жизненным циклом загрузки, карточек, интервью, подтверждений и перерасчётов. Rule Engine остаётся независимым детерминированным компонентом; LLM Agent не входит в вычислительный контур score.

## 13. Границы MVP

В MVP входят read-only ingestion, mapping и классификация строк, Data Quality, карточка процесса и `AnalysisUnit`, три стадии scoring, human confirmation, интервью, conflicts/risks/blockers, аудит, список процессов и матрица `Ценность × Реализуемость`.

В MVP не входят:

- RAG;
- Multi-Agent;
- BPMN;
- проектирование TO BE;
- автоматическое изменение официального Excel;
- детальная физическая схема PostgreSQL;
- полный публичный REST API;
- самостоятельное принятие финального решения LLM.
